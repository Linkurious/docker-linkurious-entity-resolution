# Dockerized repository

## Configuration
  - Configure variables in .env. See .env.example for template.
Reasonable defaults are provided.

## Usage
  - Run with docker-compose
    ```
    $ docker-compose up -d
    ```



## Migration to the mariadb-operator

The Bitnami MariaDB (`mariadb` values, `<release>-mariadb`) is being replaced by a MariaDB run by the
[mariadb-operator](https://github.com/mariadb-operator/mariadb-operator) (`mariadbOperator` values,
`<release>-mariadb-op`). The operator is cluster-wide and deployed from k8s-dev. Both databases run side by side
until the new one is validated:

0. Both databases must use the same existing secret (keys `mariadb-root-password`, `mariadb-password`,
   `mariadb-replication-password`), not the one generated by the Bitnami chart, which would be deleted with it.
   Copy the current Bitnami credentials into that secret first: changing the secret reference does not rotate
   credentials in an initialized database. Set **both** values, as `mariadbOperator.auth.existingSecret` is not
   derived from `mariadb.auth.existingSecret`:
   ```yaml
   mariadb:
     auth:
       existingSecret: my-mariadb-secret
   mariadbOperator:
     auth:
       existingSecret: my-mariadb-secret
   ```
   In k8s-dev, this secret is a SealedSecret (`<release>-mariadb` in preprod).
1. Before creating the destination, measure the source database's data and indexes and set
   `mariadbOperator.persistence.size` with room for MariaDB overhead and growth (the default is only `1Gi`).
   Then set `mariadbOperator.enabled: true`, `primary: false`: an empty database is created next to the Bitnami one,
   with the same secret. Entity-resolution still uses the Bitnami database.
   To keep the metrics of the Bitnami database (`mariadb.metrics`), also set `mariadbOperator.metrics.enabled: true`:
   the operator deploys a mysqld-exporter (`<release>-mariadb-op-metrics`) with its own user, and a ServiceMonitor
   labeled `release: kube-prometheus-stack` (`mariadbOperator.metrics.serviceMonitor.prometheusRelease`).
2. Rehearsal (optional): copy the data while entity-resolution keeps running, and compare row counts (differences
   are only reported, entity-resolution keeps writing):
   ```sh
   scripts/migrate-mariadb-to-operator.sh -n linkurious-entity-resolution-preprod -r linkurious-entity-resolution-develop check
   scripts/migrate-mariadb-to-operator.sh -n linkurious-entity-resolution-preprod -r linkurious-entity-resolution-develop copy
   ```
   The statefulsets are found from the release (label `app.kubernetes.io/instance=<release>`), and the MariaDB
   name is derived from the entity-resolution statefulset (the chart fullname, so `nameOverride`/`fullnameOverride`
   are taken into account). Set them explicitly with `-s` (entity-resolution statefulset), `-b` (Bitnami
   statefulset) and `-m` (MariaDB resource) if needed.
3. Stop entity-resolution: set `autoscaling.enabled: false` (if enabled) and `replicaCount: 0` in the same values
   change, then let Argo CD sync. Change the values in Git, not with `kubectl scale`: Argo CD (selfHeal) would revert
   it. Entity-resolution is unavailable from now on; restore autoscaling only after the cutover.
4. Final copy, with entity-resolution stopped:
   ```sh
   scripts/migrate-mariadb-to-operator.sh -n linkurious-entity-resolution-preprod -r linkurious-entity-resolution-develop migrate
   ```
   It refuses to run unless the statefulset has 0 replicas and no pod left, still targets the Bitnami database,
   and no client is connected to either database. Every session counts, root sessions opened with `kubectl exec`
   included: only the connections of the Bitnami metrics sidecar (identified by their client port) are ignored, so
   close any client before running it. The dump holds a global read lock on the source (`--lock-all-tables`), then the
   script compares row counts and checks again that entity-resolution stayed stopped and no client connected.
5. Restart entity-resolution on the new database: set `mariadbOperator.primary: true` **and** `replicaCount: 1` in
   the same change, and let Argo CD sync. Do not set `primary: true` before step 4 is done: entity-resolution would
   start on an incomplete copy. Once switched, it connects with the `mariadbOperator.auth.username` user
   (ALL PRIVILEGES on the database) instead of root. Check it with `check`.
   Rollback: set `primary` back to `false`. The Bitnami database is unchanged, data written on the new one is lost.
6. Once validated, set `mariadb.enabled: false`. Argo CD does not delete the PVC of the Bitnami database,
   it can be removed by hand afterwards. The existing secret of step 0 is kept, the new database still uses it.

Only the application database is copied. `check` lists the users that only exist on the Bitnami database.
